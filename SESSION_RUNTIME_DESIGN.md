# CCBox Session Runtime Design

Status: implemented with a clean cutover on 2026-08-14.

## Decision

CCBox will treat tmux as the authority for live runtimes. Each CCBox tmux session hosts at most one foreground Claude Code process. Claude Code's session UUID identifies the current conversation inside that runtime, while Claude's automatically generated title is mutable display metadata.

This will be a clean cutover. The implementation does not need to discover, migrate, or support tmux servers, session-link files, or attachment markers created by the current version.

## Goals

- List sessions across running sandboxes quickly and accurately.
- Preserve the simple operational model: one CCBox tmux session means one active Claude runtime.
- Show Claude Code's automatically generated session title once it appears.
- Associate a live tmux runtime with the exact Claude session UUID and transcript.
- Support launching a new conversation, resuming a closed conversation, and launching a fork in a separate tmux runtime.
- Remain correct when hooks are delayed, disabled, or fail.

## Non-goals

- Supporting Claude Code background agents or `claude agents`.
- Modeling subagents, teams, or parent/child agent graphs.
- Treating a Claude display title as a stable identifier.
- Preserving active runtimes across the cutover.
- Backward compatibility with the existing plain-text session-link cache or `.attached.<pid>` markers.
- Maintaining a separate CCBox history browser for closed Claude conversations.

## Identity model

There are three distinct objects:

1. **Sandbox**: an LXD container managed by CCBox.
2. **Runtime**: a live tmux session in that sandbox. Its tmux session name is the stable CCBox runtime ID for the lifetime of the process.
3. **Claude conversation**: a Claude Code session UUID that can outlive a runtime and later be resumed in another runtime.

At any instant, one runtime has zero or one current Claude conversation binding:

```text
sandbox -> tmux runtime -> Claude process -> Claude session UUID
```

The binding is not permanent. A newly launched runtime can resume a historical conversation. A fork is launched in another runtime and receives a different Claude session UUID.

CCBox should keep compact runtime names such as `s-0`, `s-1`, and so on. The runtime name is an operational identifier, not the user-facing description. It must not be renamed when Claude generates or changes its title.

## Live tmux discovery

### Shared socket

Each sandbox gets an explicit tmux socket in the existing host-mounted CCBox run directory:

```text
~/.cache/ccbox/run/tmux/<sandbox>.sock
```

All tmux operations for that sandbox must use the explicit socket with `tmux -S <path>`:

- resolving the next runtime name;
- creating sessions;
- setting session environment variables;
- attaching;
- listing sessions;
- checking whether a session still exists;
- killing one session or the server.

The socket directory is created by CCBox before starting a runtime. Socket paths must be derived from validated sandbox names, not arbitrary user paths.

### Host-side listing

The host queries the shared socket directly:

```sh
tmux -S <socket> list-sessions -F '#{session_name}|#{session_attached}|#{session_created}'
```

The no-subcommand picker performs:

1. One batched LXD API request for all container states.
2. Selection of configured sandboxes whose containers are `Running`.
3. Bounded-parallel local tmux socket queries for those sandboxes.
4. Metadata enrichment for each live runtime.

An absent, refused, or stale socket means that sandbox currently has no reachable tmux server. It must not be repaired from marker files.

Tmux is authoritative for runtime existence and attachment state. CCBox must remove the `.attached.<pid>` mechanism.

## Claude binding record

### SessionStart hook

The existing Claude Code `SessionStart` hook remains the mechanism for learning which Claude conversation is running inside a tmux runtime. CCBox already injects these environment variables into the runtime:

```text
CCBOX_SANDBOX
CCBOX_TMUX_SESSION
```

The hook reads its JSON payload from standard input and records at least:

- `session_id`;
- `transcript_path`;
- `cwd`;
- `source`, when present;
- the CCBox sandbox and tmux session from the environment;
- an update timestamp generated by CCBox.

The binding file is:

```text
~/.cache/ccbox/run/session-bindings/<sandbox>/<tmux-session>.json
```

Example:

```json
{
  "schema": 1,
  "sandbox": "stageflow",
  "runtime": "s-2",
  "session_id": "9145f0d1-d53f-42a0-ac9a-dc1542e47e57",
  "transcript_path": "/home/zj/.claude/projects/.../9145f0d1-d53f-42a0-ac9a-dc1542e47e57.jsonl",
  "cwd": "/home/zj/Projects/CXR/AutoSWE/StageFlow",
  "source": "resume",
  "updated_at": "2026-08-08T12:00:00Z"
}
```

Writes must be atomic: write a sibling temporary file, flush and close it, then replace the destination. The hook should validate that sandbox/runtime values are safe path components and that required payload fields are strings.

### Reliability boundary

`SessionStart` is sufficiently informative for binding a runtime to a Claude UUID and transcript, including fresh launches and resumed conversations. It is not a reliable lifecycle authority because hooks can be delayed, disabled, misconfigured, or interrupted.

Consequently:

- A live tmux runtime with no binding file is still displayed.
- A binding file without a live tmux runtime is stale and is not displayed.
- `SessionEnd` and normal-exit cleanup are optional hygiene, not correctness requirements.
- Listing reconciles stale binding files against the live tmux set and may prune them.
- Failure of the binding hook must not terminate or hide the Claude runtime.

No binding record is created before Claude starts. The short interval before the hook fires is represented as an untitled/unbound live runtime.

## Automatic title discovery

CCBox will not pass `--name` and will not derive a name from the user's last prompt.

Claude writes automatically generated titles into its transcript as records of the form:

```json
{"type":"ai-title","aiTitle":"Explain install.sh services and hooks","sessionId":"..."}
```

For each live runtime with a binding:

1. Read only a bounded tail of the transcript, not the complete transcript.
2. Scan JSONL records from newest to oldest.
3. Use the newest valid `ai-title` whose `sessionId` matches the binding UUID.
4. If no title is present yet, display an untitled fallback.

Suggested display:

```text
stageflow/s-2  Explain install.sh services and hooks
stageflow/s-3  (untitled)
```

The title is mutable metadata. It should be refreshed when the picker is opened rather than persisted as identity. A small in-process cache keyed by transcript path plus file size/mtime is acceptable if title reads become measurable.

The older last-prompt, branch, message-count, and relative-time transcript parsing can be removed from the primary picker. It may be retained only if another command still has a clear use for it.

## Runtime lifecycle

### New conversation

1. Resolve/start the sandbox.
2. Create a new tmux runtime using the sandbox's explicit socket.
3. Launch Claude without `--name`.
4. Display the runtime immediately by live tmux discovery.
5. `SessionStart` writes the UUID/transcript binding.
6. The picker begins showing the auto-title after Claude writes `ai-title`.

### Resume historical conversation

1. Create a new tmux runtime.
2. Launch `claude --resume <session-id>` in it.
3. `SessionStart` overwrites that runtime's binding with the resumed UUID and transcript path.
4. The title is read from the resumed transcript.

The historical conversation does not retain ownership of its old runtime. The new runtime is the live attachment point.

### Fork

The user launches the fork as a separate CCBox runtime using Claude's resume/fork arguments. The new Claude UUID received by `SessionStart` is bound to that new runtime. CCBox does not need a parent/child relationship for listing or attachment.

### Detach

Detaching changes only tmux's live attached count. No file marker is written. The runtime and binding remain available.

### Natural exit or kill

When Claude exits, the pane command exits and the tmux session disappears. The host may read the binding before cleanup to print a precise resume command. Binding cleanup can then run, but stale files are harmless because live listing is based on tmux.

### Sandbox stop or removal

Stopping the container destroys its tmux server. CCBox removes that sandbox's socket and binding directory after the stop succeeds. Sandbox removal performs the same cleanup.

## Picker behavior

The picker is built from live runtimes, then enriched with optional binding/title data.

Display priority:

1. Claude automatic title.
2. `(untitled)` when Claude is bound but has not generated a title.
3. `(starting)` or no detail when the `SessionStart` binding has not arrived.

Optional secondary detail may include attached/detached state and abbreviated Claude UUID. The UUID should not dominate normal interaction.

Sorting should use live tmux creation time initially. If a reliable transcript modification time is available, the picker may sort by recent Claude activity, but sorting must not require full transcript parsing.

If a runtime exits between display and selection, attach should refresh once and report that the runtime ended.

## Proposed code structure

### `config.py`

Add paths for:

```text
TMUX_SOCKET_DIR = RUN_DIR / "tmux"
SESSION_BINDING_DIR = RUN_DIR / "session-bindings"
```

Remove `SESSION_LINK_DIR` after all callers are migrated.

### `session.py`

- Centralize construction of the per-sandbox socket path.
- Add the explicit socket to every tmux command.
- Add host-local `list_sessions_from_socket()`.
- Add bounded-parallel `list_all_sessions()` orchestration or expose primitives for the picker.
- Remove cached session-name functions and attached marker functions.
- Replace link readers/cleaners with binding readers/cleaners.

### `cli.py`

- Replace `_session-link` with `_session-bind` or update its semantics.
- Make the hook write the JSON binding atomically.
- Make `sessions`, attach-all, kill, and resume hints use live tmux plus bindings.
- Remove marker-based cleanup and mismatch warnings.

### `picker.py`

- Collect sessions from live socket queries rather than directory enumeration.
- Read automatic titles from bounded transcript tails.
- Display starting/untitled runtimes without excluding them.
- Remove last-prompt-based naming from the primary picker.

### `transcript.py`

Add a narrow helper such as:

```python
read_latest_ai_title(path: str, session_id: str, max_tail_bytes: int = ...) -> str | None
```

The helper must tolerate partial first lines caused by seeking into the middle of a JSONL file, malformed records, file replacement, and a transcript that is still being appended.

## Testing plan

### Unit tests

- Binding payload validation and atomic replacement.
- Binding rewrite on resume with a different session UUID.
- Safe sandbox/runtime path validation.
- Latest matching `ai-title` extraction from a transcript tail.
- Missing title, malformed JSONL, partial first tail line, and title updates.
- Socket command construction always includes the sandbox socket.
- Live runtime without binding remains visible.
- Stale binding without runtime is excluded and prunable.
- Attached state comes from tmux output.
- Attach race refresh behavior.

### Integration test after cutover

With all old sessions stopped:

1. Start a fresh Claude runtime and immediately list sessions before entering a prompt.
2. Enter prompts until Claude generates a title; reopen the picker and verify the title appears.
3. Detach and confirm the runtime is listed as detached.
4. Reattach and confirm the same runtime and Claude conversation continue.
5. Exit Claude and confirm the runtime disappears and a valid resume command is printed.
6. Resume the closed conversation in a new runtime and confirm the same Claude UUID/title bind to the new runtime.
7. Fork into another new runtime and confirm both live runtimes have distinct UUIDs.
8. Kill a tmux session externally and confirm no ghost entry remains.
9. Temporarily disable or break the hook and confirm the live runtime appears as starting/unbound.
10. Stop a sandbox and confirm its socket and bindings are cleaned.
11. Measure no-subcommand picker startup across all running sandboxes and compare it with the current implementation.

## Cutover checklist

Implementation should begin only after the user confirms all existing CCBox tmux sessions can be stopped.

At cutover:

1. Stop all CCBox tmux servers/sessions.
2. Remove the old session-link and attachment-marker directories.
3. Deploy the explicit-socket implementation and updated hook command.
4. Start new runtimes only through the new CCBox version.
5. Run the integration test above before relying on the picker.

Because this is a single-user clean cutover, the implementation should prefer a small, strict design over legacy detection, dual reads, schema migration, or fallback `lxc exec` support for old tmux servers.
